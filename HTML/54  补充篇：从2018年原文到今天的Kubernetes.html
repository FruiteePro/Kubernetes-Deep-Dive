编者补充 · 2026 年 9 月：本篇由仓库维护者追加，不属于张磊在极客时间发表的专栏原文。原有 00—53 篇主要写于 2018 年；容器、Pod、控制器、声明式 API 等核心思想依然值得学习，但实验功能、安装命令、资源版本和一些实现细节不能不加核对地照搬到今天的集群。

下面按原文章节归纳最影响复现、安全和理解的时效性差异。“已移除”指 Kubernetes 不再提供那项 API 或机制；“已弃用”不等于立刻不能用；“实现演进”则表示原文在当时成立，只是现在另有主流做法。这里不是逐个命令的替换脚本：真正迁移前，仍需核对目标集群版本、发行版、CNI/CSI 驱动和 Istio 版本。

一、不要直接照抄的安装和运行时步骤

  • 第 10、11 讲：安装仓库与 kubeadm。 原文基于 Ubuntu 16.04、apt.kubernetes.io、apt-key、旧 kubeadm.k8s.io/v1alpha* 配置以及旧镜像和网络插件清单。旧软件仓库已停止提供新包；现在按目标 Kubernetes 小版本选择 pkgs.k8s.io 软件源，按该版本的官方 kubeadm 安装文档准备 CRI、CNI、镜像和配置（当前文档使用 kubeadm.k8s.io/v1beta4，不能保证适用于所有旧版本）。不要把原文指向 GitHub master 分支的在线 YAML 直接应用到生产集群；应固定与集群兼容的发布版本并审阅清单。参阅 安装 kubeadm和软件源迁移。
  • 第 05—08、45、46 讲：Docker、dockershim 和 cgroups。 原文使用 Docker Engine 与 kubelet 内置 dockershim 解释当年的实现。从 Kubernetes 1.24 起，kubelet 已移除 dockershim；节点一般使用实现 CRI 的 containerd 或 CRI-O，需要保留 Docker Engine 时须另行配置 cri-dockerd。这不影响 Kubernetes 运行用 Docker 等工具构建的兼容容器镜像。书中的 cgroup v1 文件路径和命令也应视为历史演示：新版节点多用 cgroup v2，Kubernetes 1.35 起弃用 cgroup v1，kubelet 默认不在 cgroup v1 节点启动；管理员虽可暂设 failCgroupV1: false，仍应迁移至 cgroup v2。参阅 1.24 发行说明、cgroup v1 弃用说明。

二、曾经的自动改写对象机制，如今怎么做

  • 第 15 讲的 PodPreset：已移除。 文中的 settings.k8s.io/v1alpha1 PodPreset 是实验性机制，不应再用它向匹配标签的 Pod 注入环境变量、卷和挂载。确定性的公共配置可以写进 Deployment 的 Pod 模板，或用 Helm/Kustomize 管理；必须在创建 Pod 时按条件动态修改对象，使用 Mutating Admission Webhook。
  • 第 23 讲的 Initializer：已移除。 InitializerConfiguration 和 metadata.initializers.pending 属于旧的异步初始化机制，不是现代 Kubernetes 可部署的配置。现在为 Pod 注入 sidecar 的典型路径是：API Server 在创建 Pod 的准入阶段调用已注册的 Mutating Webhook → 注入服务返回补丁 → API Server 修改对象后创建 Pod；不需要控制器事后清除 pending。文中 initializer.kubernetes.io/envoy: "true" 也不是 Kubernetes 自动识别控制器的通用开关，只有注入控制器约定读取它才有作用；名为 envoy-initializer 的 ConfigMap 只是供注入器读取的配置，创建它本身不会注册注入器；示例的 metadata 还漏了冒号。这不代表 2018 年没有 Webhook：Kubernetes 1.9 时准入 Webhook 已是 Beta。参阅 已移除的特性门控、2018 年准入机制公告。
  • 第 23 讲的 Istio 架构图：历史版本，不是今天的部署拓扑。 Pilot、Galley、Citadel 等独立组件及独立 sidecar injector 的描述，后来被集中到 istiod；Istio 的 sidecar 自动注入仍使用 Mutating Webhook。要为命名空间内新创建的 Pod 注入，可按所装 Istio 版本配置 istio-injection=enabled 或修订标签 istio.io/rev；针对单个 Pod 常用 sidecar.istio.io/inject: "true" / "false" 标签，Deployment 中要写在 spec.template.metadata.labels。已有 Pod 不会因修改标签而原地增加 sidecar。并且今天 Istio 还有无需逐 Pod sidecar 的 ambient 模式（ztunnel，按需使用 waypoint），因此“服务网格必然等于每个 Pod 都有 Envoy”也只适用于该文讨论的 sidecar 模式。参阅 istiod 变迁、当前注入方式、ambient 模式。
  • 第 23、24、25 讲的 PATCH/声明式 API：原理仍有价值，工具链已有新选择。 不应把文中的 TwoWayMergePatch 伪代码看成编写现代控制器的唯一实现，也不要以为 kubectl apply 一律已自动改用服务器端。Server-Side Apply 在 Kubernetes 1.22 GA，服务端通过 managedFields 跟踪字段所有权并报告冲突；需要显式选择时使用 kubectl apply --server-side，控制器也可使用 Apply API。客户端 apply、JSON Patch、Strategic Merge Patch 仍是不同场景下的工具，不能机械互换。

三、原文 YAML 里的旧 API 版本

以下是原文章节中的实际示例，不是说相关资源本身被废除了。原对象通常还能通过新的 API 访问，但旧清单、旧客户端请求可能直接报“找不到版本”。变更不止替换 apiVersion：特别注意必填字段、字段路径和默认行为。完整清单以 Kubernetes 的已弃用 API 迁移指南为准。

原文章节 / 写法现在的写法与迁移要点
第 31 讲：apps/v1beta2 的 DaemonSet；第 39 讲：extensions/v1beta1 的 Deployment改用 apps/v1；这两个旧 API 版本自 1.16 不再提供。spec.selector 必填，且须与 Pod 模板标签相符；创建后不可随意修改。
第 22 讲：batch/v1beta1 的 CronJob使用 batch/v1；旧版本自 1.25 不再提供。Job/CronJob 的调度思想仍成立。
第 24 讲：apiextensions.k8s.io/v1beta1 的 CRD使用 apiextensions.k8s.io/v1；旧版本自 1.22 不再提供。须使用 spec.versions、显式 spec.scope，并为版本提供结构化 openAPIV3Schema，不能只改版本字符串。
第 36 讲：extensions/v1beta1 的 NetworkPolicy使用 networking.k8s.io/v1；旧版本自 1.16 不再提供。NetworkPolicy 能否生效仍取决于网络插件是否实现它。
第 39 讲：extensions/v1beta1 的 Ingress，旧 serviceName / servicePort 字段使用 networking.k8s.io/v1；旧版本自 1.22 不再提供。后端写成 backend.service.name 与 backend.service.port.number，每条路径需 pathType；通常用 spec.ingressClassName 指定已安装的控制器。
第 49 讲：autoscaling/v2beta1 的 HPA使用 autoscaling/v2；旧版本自 1.25 不再提供，v2beta2 自 1.26 不再提供。自定义指标的 metrics[*].object 等字段结构也有调整，需参考当前示例；指标 API 仍须由对应的适配器提供。

例如，第 39 讲的茶与咖啡路由在新版 Ingress 中，核心字段应写成这样（ingressClassName 需换成集群中实际存在的 IngressClass）：

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: cafe
spec:
  ingressClassName: example-controller
  rules:
    - host: cafe.example.com
      http:
        paths:
          - path: /tea
            pathType: Prefix
            backend:
              service:
                name: tea-svc
                port:
                  number: 80
          - path: /coffee
            pathType: Prefix
            backend:
              service:
                name: coffee-svc
                port:
                  number: 80

四、功能没消失，但底层或首选方案变了

  • 第 30、31 讲：存储扩展。 PV、PVC、StorageClass 的抽象依然适用；但手工把 FlexVolume 脚本放进每台宿主机插件目录已是旧方案。FlexVolume 自 1.23 弃用，新驱动优先使用 CSI；原文 CSI 章节的早期 sidecar 镜像、API 清单及镜像版本也要随驱动发布版本一起核对，不能原样部署。参阅 卷与 FlexVolume 状态。
  • 第 37、38 讲：Service 后端列表。 Service 依靠选择器找到 Pod、readiness 影响可用后端的核心概念仍正确；但脚本或控制器不宜再依赖 kubectl get endpoints 得到唯一、完整的后端列表。Endpoints API 自 1.33 被弃用；使用 discovery.k8s.io/v1 的 EndpointSlice，并通过标签 kubernetes.io/service-name 找到一个 Service 对应的多片后端。参阅 Endpoints 迁移说明。
  • 第 37—39 讲：网络数据路径与入口。 原文 iptables 规则和“IPVS 更适合大规模 Service”的演示是当年特定实现，不是所有集群唯一的数据路径。kube-proxy 的 IPVS 模式自 1.35 弃用；Linux 下还有 iptables、nftables 等模式，具体须看集群配置和网络插件实现。Ingress API 本身没有被移除，但已冻结新功能，复杂路由可考虑有对应实现的 Gateway API。原文建议安装的社区 ingress-nginx 控制器在 2026 年 3 月后结束维护；它和 Ingress API 不是一回事，应评估受维护的控制器及迁移路径，而不是继续套用其 master 安装清单。参阅 IPVS 与 ingress-nginx 公告、Ingress 状态、Gateway API。
  • 第 41—43 讲：调度器扩展。 “过滤候选节点、为可行节点打分、必要时抢占”的思路仍正确；原文 Predicate/Priority 的具体函数与扩展方式属于历史实现。配置和编写新扩展应查看当前 Scheduling Framework 的 Filter、Score、PostFilter 等插件扩展点，而不是直接套用旧调度策略或源码路径。
  • 第 26 讲：ServiceAccount Token。 原文称创建 ServiceAccount 后会自动生成长期有效的 Token Secret；现代集群不应据此读取 serviceAccount.secrets[0]。Pod 中的凭据主要通过 kubelet 使用 TokenRequest 取得、以 projected volume 挂载的短期可轮换令牌提供；集群外临时取令牌可用 kubectl create token。长效 Secret 可以手动创建，但并非默认做法。参阅 管理 ServiceAccount。
  • 第 49 讲：自定义指标示例的授权。 为了用 curl 快速读指标，原文把读取权限绑定给 system:anonymous。这是当年的实验步骤，不要在真实集群执行：它会让匿名请求得到本不应有的权限。应通过正确身份认证，给特定 ServiceAccount/用户最小权限的 Role/ClusterRoleBinding；使用 HPA 时检查 Metrics Server 或 custom-metrics adapter 的实际 API/RBAC。权限原则参阅 RBAC 文档。

五、如何安全地使用这套旧教程

  1. 学概念时保留原文的时间背景；特别是第 01—04 讲的 Docker、rkt 和编排竞争史，它们是明确标年的历史，不是当前产品推荐清单。
  2. 复制任何 YAML 之前先看集群版本：kubectl version、kubectl api-resources、kubectl api-versions；按目标版本的官方文档修改 API 和字段，再在测试环境使用 kubectl apply --dry-run=server -f <文件> 校验。服务端 dry-run 只检查请求与准入行为，不代替控制器、CNI、CSI 的真实运行验证。
  3. 不要把网上的旧 master 安装清单、跨版本镜像、匿名授权命令直接用于生产。迁移时区分对象版本已移除、实现仍在但已弃用和只是不再推荐；最终以实际发行版的兼容矩阵和升级文档为准。
